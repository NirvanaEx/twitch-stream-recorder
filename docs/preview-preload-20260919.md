# Предзагрузка превью — 19 сентября 2026

При открытии записи `VideoPlayer` запускает `useTimelinePreload`. Кадры собраны
в WebP-листы по 100 изображений 320×180: для текущих записей это 15–22 запроса
и примерно 9–11 МБ вместо тысяч отдельных запросов при наведении.

Две загрузки выполняются параллельно с низким сетевым приоритетом. Готовые листы
хранятся как Blob URL до закрытия плеера. Наведение меняет область отображаемого
листа; сетевой запрос для готового листа не нужен. Первичная загрузка занимает
время, зависящее от соединения: в проверке последней записи — 5,1 секунды.
При смене записи запросы отменяются и память освобождается. Ошибки загрузки
повторяются один раз; затем остаётся обычная загрузка изображения по запросу.
Если лист недоступен, плеер использует прежнее отдельное JPEG-превью.

Фоновый генератор теперь вызывает `apps/api/scripts/timeline-sprites.cjs`.
Листы строятся из готовых JPEG, исходное видео повторно не читается. Манифест
публикует сведения о листах после завершения упаковки. Прежний systemd-таймер
`stream-timeline-previews.timer` сохранён, запуск нового генератора проверен.

Рабочая копия сервера:
`/root/projects/twitch-stream-recorder-preview-preload-20260919`.
Образы: API `twitch-stream-recorder-api:preview-preload-r2-20260919`,
web `twitch-stream-recorder-web:preview-preload-r2-20260919`.
Файлы релиза и отката — `release-r3.json`, `compose.preload.yml`,
`compose.rollback.yml`; выкладка — `deploy-preload-r3.py`.
Исходники учитывают текущую серверную версию и предыдущую доработку превью;
при следующей полной сборке проекта их необходимо включить в исходную ветку.

Проверки: TypeScript и Next.js build; тесты ограниченного параллелизма,
повторной загрузки, отмены, очистки Blob URL и границ листов; тесты проверки
метаданных и путей файлов; запуск готового веб-образа в отдельном контейнере;
выдача WebP работающим API. В браузере все 15 листов новой записи загружены до
наведения; четыре позиции таймлайна показаны из Blob URL с нулём новых
HTTP-запросов при наведении.

Та же проверка пройдена для записей от 15 и 16 сентября (22 и 16 листов):
начало, середина и конец показаны из памяти, новых запросов при наведении — 0.
Повтор после ошибки использует `cache: reload`, чтобы не застревать на
сохранённом браузером ответе 404; успешные ответы используют обычный HTTP-кэш.
