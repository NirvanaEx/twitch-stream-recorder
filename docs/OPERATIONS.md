# Обновление API без остановки записи

## Что работает

`twitch-recorder-api` сохранён без пересоздания и теперь служит постоянным
рекордером и обработчиком медиа. Историческое имя сохранено для совместимости
с `tsr-sync`, retention, таймером превью и существующей Docker DNS-записью.
Он владеет Streamlink/FFmpeg, соединениями чата, Telegram и очередями выгрузки.
Его дополнительные старые HTTP-маршруты не являются основным API сайта.

Публичный HTTP API работает в отдельном контейнере `tsr-http-api-<release>`.
Nginx направляет `/api/` к нему; WebSocket соединения остаются на постоянном
рекордере. `TSR_ROLE=api` запрещает запуск/восстановление записей, фоновых
выгрузок, очистку их временных файлов и создание нового Telegram-клиента.
Общий каталог `/data` и архив `/mnt` у API подключены только для чтения.

API читает каталог, чат, пользователей, настройки и состояние сессий из общей
PostgreSQL. Команды каналов/записи, обслуживание архива, медиа, GIF-экспорт,
живые эмоуты и Telegram проходят по существующему REST-контракту v1 к рекордеру
с исходной авторизацией пользователя. После рестарта API повторно соединяется
с владельцем; не помечает активные сессии остановленными и не начинает их заново.
При недоступности владельца команды возвращают 503, автоматического повтора нет.

Первое включение этой схемы намеренно не обновляет исполняемый код рекордера:
живое соединение с источником и процесс FFmpeg невозможно перенести простым
копированием файлов. Новый HTTP API совместим с уже запущенным рекордером.
В исходниках роли `api`, `recorder`, `standalone` выделены явно; production без
явной роли завершится до инициализации сервисов. Отдельный рекордер остаётся
постоянным, а не временным контейнером на время выкладки.

## Обычная выкладка API

```sh
cd /root/projects/twitch-stream-recorder-current
python3 ops/deploy-api.py
```

Скрипт сверяет package/schema с работающим рекордером, компилирует и запускает
тесты без сети и производственных данных, создаёт слой на точном текущем
образе зависимостей, запускает новый API и проверяет роль/связь с рекордером.
Затем меняет только upstream HTTP API через graceful reload Nginx. Предыдущий
API останавливается после успешного переключения и сохраняется для отката.
Рекордер, БД, web, синхронизация и WebSocket соединения не перезапускаются.

Откат: `python3 ops/deploy-api.py --rollback`. Для самого первого выпуска
откат возвращает маршрутизацию к исходному процессу без его рестарта.

API не выполняет `prisma db push` при старте. Изменения схемы должны сохранять
совместимость с текущим рекордером: сначала добавлять новые поля/таблицы,
переводить потребителей, удалять старые поля только после обновления всех ролей.

## Обновление интерфейса

Сборка интерфейса выполняется отдельно, после проверки её актуальных исходников.
При использовании существующего Compose обновлять только `web` с `--no-deps`
и нужным образом. Не включать `api` в эту команду: в старом Compose это рекордер.
Не использовать старые скрипты, одновременно обновляющие `api web`.
Допустима краткая недоступность интерфейса; запись от этого не зависит.

## Проверка непрерывности

`python3 ops/verify-isolation.py` действительно перезапускает только новый API,
проверяет его повторное подключение, авторизацию, маршрутизацию команд для
несуществующего канала, неизменность сессий/PID рекордера и рост счётчика записи.
Секреты не выводятся. Отчёт сохраняется в каталоге текущего выпуска.

`GET /api/health` показывает роль API, отсутствие фоновых заданий и связь с
рекордером. Это проверка доступности процесса, а не гарантия качества источника.
При обрыве связи API никогда не присваивает себе задания рекордера.

## Обновление самого рекордера

Это отдельное обслуживание. Текущая реализация изолирует его от всех обновлений
API/web, но не обещает непрерывность при его собственном перезапуске или рестарте
VPS. Перед заменой рекордера дождаться окончания захватов и выгрузок, проверить
совместимость новой версии, затем заменить единственного владельца. Не запускать
два рекордера с общей БД/каталогом. Одновременное завершение эфиров старой версией
и начало новых на другой потребует отдельного распределения владения заданиями;
оно не включено в эту доработку.
